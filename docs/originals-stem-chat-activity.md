# Stem activity in project chat

New instrument/foundation submissions and accepted contributions post distinct Project update entries in the existing group chat. Submitted entries show the role and stem count; approved entries show a green confirmation. They use first name and surname initial, or the chosen anonymous credit. No file names, attachments, private notes, email addresses or legal names are copied into these entries. Uploading a file alone, failed submissions, rejections and mix/master outputs do not create stem activity.

`submittedChatPending` is committed with a new contribution in its submission transaction. `approvedChatPending` is saved with an accepted decision. Each action attempts to publish immediately after saving. Chat failures leave the successful contribution/decision intact; the minute notification worker recovers pending activity independently of optional workflow automation. The existing unique project/author/client-message index deduplicates entries, using a server-reserved `system:` namespace that the normal chat endpoint refuses. No new message index is required. Pending markers are cleared only after the chat entry is stored.

Entries use their posting time and native message IDs so recovered activity appears as unread through the existing chat cursor. System entries join the existing group-chat email outbox, whose membership checks exclude people whose participation has ended. The person performing the action is excluded by the existing author rules. Existing separate owner submission emails remain in place. No historical chat backfill is performed for submissions without a pending marker.

Deploy backend and admin together to enable the new entry styling. Validation covers real controller submission/approval with fixture storage, retry/recovery and concurrency, anonymous credits, absence of private material, user spoof prevention, unread/read acknowledgements, ordinary chat rendering and mobile layout. All validation uses local fixtures; no live messages or emails are sent.
